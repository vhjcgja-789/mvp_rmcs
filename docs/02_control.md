1. **按配方搬**。照 `architecture.md` §4.2 的迁移配方处理:`update()` 的函数体原样搬,`*input_` 改成读 state handle,`*output_ = x` 改成写 command handle 或导出接口。参数名尽量和 RMCS 的 yaml 一致。
2. **锁定 1 kHz**。RMCS 的 PID 没有 dt,很多地方也写死了 1 kHz(`kDt = 1e-3`、`0.001 / T`、`×1000` 的拍数换算)。每个搬过来的控制器都在 `on_configure` 里检查 `update_rate == 1000`,不满足就拒绝配置。这一行是内容本身的前提,不算工程细节。
3. **纯算法头文件原样复制**,删掉 ROS 和 executor 的 include,放进 `mvp_controllers/include/mvp_controllers/<领域>/`,文件头注明来源。可以直接复制的有:
   - `matrix_pid_calculator.hpp`、`qcp_solver.hpp`;
   - `filter/low_pass_filter.hpp`、`alpha_beta_angle_filter.hpp`;
   - fast_tf 核心和 `sentry_description.hpp`(Eigen 实现)。
4. **失能信号统一读 `safety/enabled`**,这个接口由 01 阶段 9 的 SafetyController 导出。控制器靠它做失能时的状态捕获和 PID 复位(RMCS 里每个控制器都自己判断拨杆)。真正断电是硬件层的事。
5. **NaN 表示"不控制"**:控制器输出 NaN,硬件就发 0 电流。

# A. 舵轮底盘

内容来源:`chassis/steering_wheel_controller.cpp`(下文简称 SWC)、`chassis_controller.cpp`(CC)、`chassis_power_controller.cpp`(CPC)、`qcp_solver.hpp`(QCP);参数在 `rmcs_bringup/config/sentry.yaml` 第 104–193 行。

## A1 — 单个舵向:用力矩电机保持角度

- **需求(问题)**:GM6020 舵向运行在电流(力矩)模式,首先要能让它停在指定角度。
- **方法选择 + 原因**:
  - 用 01 阶段 4 的两个链式 PidController 做串级:角度环(kp 30)→ 速度环(kp 0.15)→ effort。增益直接取 SWC 的值。
  - 现在先不写专用控制器,用现成的串级验证增益和方向是否正确。
- **具体实现**:只改 `controllers.yaml`,作用于关节 `chassis_steer_lb`。
- **验证**:给 0、π/2、−π/2 三个目标,都能平稳停住;手推舵向后能自动回位。

## A2 — 单个轮速环

- **需求(问题)**:轮子要能跟踪目标转速。
- **方法选择 + 原因**:用 PidController(kp 0.5,取自 SWC 第 401–402 行),仍然是现成部件。
- **具体实现**:只改 `controllers.yaml`,作用于关节 `chassis_wheel_lb`。
- **验证**:给 10 rad/s,能稳定跟住。

## A3 — 一个舵轮模块:180° 折叠

- **需求(问题)**:目标方向从 +80° 变到 −100° 时,舵向会转整整 180°。其实只要把轮子反转、舵向转 0° 就够了。
- **方法选择 + 原因**:
  - 折叠需要舵向和轮向一起决策,两个独立的 PID 表达不了,所以从这里开始写专用的 `SteeringWheelController`。它直接占用一个模块的舵向和轮向 effort,内部做串级。
  - 搬 SWC 的做法:
    - 角度误差对 π 取模,折叠到 [−π/2, π/2](第 533–541 行;注释里写的 "[0,π)" 是错的);
    - 轮速目标投影到舵向的**实际**朝向(第 393–403 行)。这一步同时完成了自动反转,以及舵向还没转到位时按 cos 降速。
- **具体实现**:
  - 控制器导出参考接口 `chassis/vx`、`chassis/vy`(这一阶段只用一个模块);
  - 舵向串级写法是 `τ = Kv·(Ka·err − ω)`,这一阶段不加前馈;
  - 移植约定第 2 条的 1 kHz 检查从这里开始加。
- **验证**:目标方向在 ±100° 之间来回切换,舵向始终不超过 90°,轮子会自动反转。

## A4 — 四个模块 + 逆运动学

- **需求(问题)**:要让整个底盘按 (vx, vy, wz) 运动。
- **方法选择 + 原因**:
  - 搬 SWC 的运动学:每个轮子的线速度 `u_i = v + ω × r_i`,舵向目标取 `atan2`。
  - 计算全部在旋转了 −45° 的坐标系里做,轮子正好落在 0°/90°/180°/270°(第 177、291、357 行)。这个约定原样保留,不重新推导,以免引入符号错误。
- **具体实现**:
  - 控制器扩展到 8 个 effort;
  - 新增参考接口 `chassis/wz`;
  - 参数 `vehicle_radius` 0.2687、`wheel_radius` 0.055。
- **验证**:先架空车体,分别发纯平移、纯旋转、平移加旋转,观察四个舵向的朝向是否正确;再落地低速开动。

## A5 — 静止不抖:舵向被动

- **需求(问题)**:速度为 0 时 `atan2(0, 0)` 没有定义,舵向会抖。
- **方法选择 + 原因**:搬 SWC 第 510–527、544 行的做法:`|u|²` 很小时,舵向目标改为加速度方向;如果加速度也没有,目标就是 NaN,舵向输出 0 力矩,处于被动状态。
- **具体实现**:几行条件分支。
- **验证**:停车后舵向安静,不抖动;起步时舵向先朝加速度方向转。

## A6 — 里程计(正运动学)

- **需求(问题)**:后续的参考模型、能量钳位、调试和导航对照,都需要底盘的实测速度。
- **方法选择 + 原因**:搬 SWC 第 319–331 行。源码注释写的是"逆运动学",实际计算的是从轮子到车体的正运动学。结果导出为状态接口,便于观察。
- **具体实现**:导出 `chassis/measured_{vx,vy,wz}`,并加入 01 阶段 17 的 InterfaceBroadcaster。
- **验证**:手推车体时,读数的方向和量级都正确。

## A7 — 遥控开车(ChassisController 最小版)

- **需求(问题)**:要用遥控器开车。
- **方法选择 + 原因**:
  - 写 `ChassisController`,作为 SWC 的上游链式控制器,写入 SWC 的 vx / vy / wz 参考接口。
  - 摇杆映射搬 CC 第 181–206 行,但最大速度先用一个现实的值(参数 `max_velocity`,例如 2 m/s)。RMCS 用的是 20 m/s,真正的限制来自功率约束 QCP,而现在还没有这一层(A14 才有)。
  - 失能时输出 NaN,SWC 收到后复位(SWC 第 109–112 行)。
  - 模式、云台系、导航都留到后面。
- **具体实现**:ChassisController 读 `remote/*` 和 `safety/enabled` 两组接口。
- **验证**:遥控能开车;双拨杆拨到下,车立刻无力。

> 到这里,底盘已经可以遥控开动。A8–A14 是动力学和约束,等 01 阶段 16(实测功率)就绪后再做。

## A8 — 参考模型 + 速度环输出加速度

- **需求(问题)**:直接把目标速度交给轮速环时,起步发冲,而且加速度没有上限;后续的功率和摩擦约束也需要"期望加速度"这个量才能施加。
- **方法选择 + 原因**:
  - 搬 SWC 的结构:维护一个参考模型 `chassis_velocity_expected_`,先用底盘速度 PID(平移 20/0.001/0、角速度 5/0/1)计算期望加速度,再对加速度积分,更新参考模型(第 364–390、592–595 行)。
  - 加速度死区 0.1 也一起搬过来。
- **具体实现**:SWC 中间插入"模型 → 加速度"这一层,轮速环改为跟踪模型速度。
- **验证**:阶跃速度指令下,速度曲线变成平滑斜坡,不再有冲击。

## A9 — 轮力矩前馈(质量、转动惯量)

- **需求(问题)**:加速时只靠轮速 PID 出力,跟踪会滞后。
- **方法选择 + 原因**:
  - 搬 SWC 第 555–575 行:`τ_ff = r·(m·a 的投影 + J·α·sin(α − φ)/R) / 4`。
  - 参数 m = 22、J = 0.7785 先沿用 RMCS 的值。如果换了车,要重新辨识。
- **具体实现**:轮向输出改为前馈加 PID。
- **验证**:加速段的跟踪误差明显小于 A8。

## A10 — 舵向角速度前馈

- **需求(问题)**:走曲线时舵向跟不上,轮子方向滞后。
- **方法选择 + 原因**:搬 SWC 第 503–506 行,`dθ/dt = (u × u̇) / |u|²`,包含车体自转带来的项。
- **具体实现**:舵向串级里加上 ff 项。
- **验证**:走圆弧时,舵向角误差变小。

## A11 — 小陀螺时平移方向抹开:在 odom 系计算

- **需求(问题)**:底盘边自转边平移时,如果参考模型在车体系里积分,平移方向会被"抹开",车走弧线。
- **方法选择 + 原因**:
  - 搬 SWC 的做法(对应 RMCS 提交 f0077b6c):用底盘陀螺积分出 yaw(第 274–277 行),把参考模型和 5 Hz 低通滤波都放在 odom 系里计算(第 143–145、593 行)。
  - 需要 01 阶段 10 的底盘 IMU。
- **具体实现**:读 `chassis_imu/angular_velocity.z`,同时引入 `low_pass_filter.hpp`。
- **验证**:边自转边平移,轨迹是直线。

## A12 — 堵转或打滑时模型卷绕:能量钳位

- **需求(问题)**:车被挡住时,参考模型的速度会越积越大,一旦脱困就会猛冲出去。
- **方法选择 + 原因**:搬 SWC 第 333–343 行。当模型的动能 `m·v² + J·ω²` 超过实测动能时,按 `√(E_实测 / E_模型)` 缩放模型速度。实测动能来自 A6 的里程计。
- **具体实现**:十来行代码。
- **验证**:顶墙时推几秒再松开,车不会猛冲。

## A13 — 打滑:摩擦菱形约束

- **需求(问题)**:加速度过大时轮子会打滑。
- **方法选择 + 原因**:
  - 先只搬 QCP 里的线性约束部分:摩擦菱形 `μg` 和 `μg·m·R/J`(SWC 第 421–423 行;QCP 第 172–279 行,Sutherland–Hodgman 多边形裁剪)。
  - 功率椭圆留到下一阶段,一次只加一种约束。
- **具体实现**:
  - 复制 `qcp_solver.hpp`;
  - QCP 遇到异常输入时会调用 `std::terminate`(第 362、448 行),在实时线程里不能保留,改成返回零加速度。
- **验证**:全油门起步时轮子不打滑(看实测速度和轮速是否一致)。

## A14 — 功率模型 + 完整 QCP(功率上限先用固定值)

- **需求(问题)**:比赛有底盘功率上限,超了会被扣血。
- **方法选择 + 原因**:
  - 搬 SWC 第 131–132 和 406–481 行的功率模型:`P = Σ(τ·ω + k1·τ²) + k2·Σω² + P0`,把功率约束写成椭圆,交给 QCP 求闭式解。
  - 功率上限先用参数里的固定值,裁判系统闭环留到 A18。
  - k1 / k2 / P0 需要用 01 阶段 16 的实测功率重新辨识。
- **具体实现**:SWC 读入 `chassis/control_power_limit`。现阶段由一个参数常量提供,以后改成由 CPC 写入。
- **验证**:全油门时实测功率不超过设定上限。

## A15 — 底盘模式:小陀螺

- **需求(问题)**:哨兵需要小陀螺来规避打击。
- **方法选择 + 原因**:

- **验证**:按规定的拨杆序列能进入和退出小陀螺;结合 A11,边转边走仍然是直线。

## A16 — 云台系平移 + 跟随云台(STEP_DOWN / LAUNCH_RAMP / ALIGNMENT)

- **需求(问题)**:"前进"应该指云台朝向,而不是车头;非小陀螺模式下,车头要跟随云台。
- **方法选择 + 原因**:
  - 搬 CC 第 197–198 行(平移向量按大 Yaw 编码器角旋转)和第 226–291 行(跟随 PID,kp 8、ki 0.001)。
  - 跟随的误差用"云台目标相对底盘的角度",也就是 `gimbal/yaw_control_error + gimbal/yaw_angle`,所以底盘追的是云台要去的方向,而不是云台现在的方向。
  - 这两个量由 B9 导出。
- **具体实现**:ChassisController 读 B9 的接口,补上其余模式和键盘的切换边沿(CC 第 131–148 行)。
- **验证**:转动云台后车头跟着转;推前进时,车沿云台朝向走。

## A17 — 导航速度接入(依赖 04)

- **需求(问题)**:导航发出的 `cmd_vel` 要能驱动底盘,并且不能和遥控打架。
- **方法选择 + 原因**:
  - 用 01 阶段 17 的参考量入口:超时 500 ms 后置零;导航速度和遥控速度相加;导航给出的行为覆盖当前模式。这与 RMCS(CC 第 115–119、184–190 行)行为一致。
  - 导航的 `cmd_vel` 在 `base_link` 下。如果 03 阶段 1 确认 `base_link` 是大 Yaw 台,就按大 Yaw 编码器角旋转到底盘系,和 RMCS 的做法相同。
  - 放行条件(RMCS 里是右拨杆在 UP)放在环内的 ChassisController,不放在决策节点。理由是这和安全相关。
- **具体实现**:ChassisController 增加 `cmd_vel` 和 `chassis_behavior` 两个参考入口。
- **验证**:用 `ros2 topic pub` 发速度,车动起来;停发 0.5 s 后车停下;右拨杆不在 UP 时导航指令无效。

## A18 — 裁判功率上限 + 虚拟缓冲闭环

- **需求(问题)**:固定的功率上限要么太保守,要么超限,需要按裁判给的上限和缓冲能量闭环调节。
- **方法选择 + 原因**:
  - 搬 CPC 第 119–161 行(不含 boost):
    - 虚拟缓冲 `E_v += dt·(P_期望 − P_实测)`,钳位在 [0, min(E_裁判, 30)];
    - 功率上限乘以 `E_v / 30`。
  - CPC 做成独立控制器,写入 SWC 的 `control_power_limit` 参考接口。
  - 修 RMCS 的问题:`virtual_buffer_energy_` 和 `chassis_power_limit_expected_` 没有初始化(第 183、196 行)。
- **具体实现**:读 01 阶段 15 的裁判接口和阶段 16 的实测功率。
- **验证**:全油门持续行驶时,缓冲能量不会被耗尽。

## A19 — 超电:充电、boost、电压混合

- **需求(问题)**:要用超电在需要时提供超出功率上限的爆发。
- **方法选择 + 原因**:
  - 搬 CPC 第 89–107 行(充电上限,写入 01 阶段 16 的 `supercap/charge_power_limit`)和第 131–153 行(boost 由 Shift 或旋钮触发;`need_power` 时不限功率;按超电电压在 12.0–12.5 V 之间平滑过渡)。

- **具体实现**:CPC 补齐这部分逻辑。
- **验证**:按 boost 时实测功率超过裁判上限,超电电压下降;电压低时自动回落到正常功率。

# B. 偏心双 Yaw 云台

内容来源:`gimbal/eccentric_dual_yaw.cpp`(下文简称 EDY,共 481 行);参数在 `sentry.yaml` 第 65–103 行。

机构:大 Yaw(MG6012,在底板上)→ 小 Yaw(MG4010,顶板;轴心偏移 0.08 m)→ pitch(MG4010,顶板)。

RMCS 的现状:
- **分工**:小 Yaw 的目标始终是 0,也就是保持居中;世界系下的瞄准全部由大 Yaw 完成(EDY 第 59、78、99 行)。
- **增益**:全部是纯 P 串级,ki 和 kd 都是 0。

## B1 — pitch 单轴串级(编码器系)

- **需求(问题)**:pitch 要能停在指定角度。
- **方法选择 + 原因**:
  - 从这一步就写专用的 `SentryGimbalController`,并占用三个轴的 effort,而不是像 A1 那样用通用 PID 链。理由有两条:后面会出现跨轴的耦合(世界系换算、小 Yaw 对大 Yaw 的反作用);RMCS 也是把三个轴放在一个组件里。
  - 先只实现 pitch 分支:EDY 第 425、430、435、470–472 行,角度 kp 32 → 速度 kp 2.5 → 力矩。
  - LK 电机的角度在 [0, 2π) 内,要先用 `remainder` 换算到 (−π, π]。
- **具体实现**:目标暂时从 `~/pitch_target` 话题读入;另外两个轴输出 NaN。
- **验证**:给几个目标,都能停住;符号约定是**正值代表枪管向下**(与 RMCS 一致)。

## B2 — pitch 重力前馈

- **需求(问题)**:纯 P 控制下枪管会下垂,存在稳态误差。
- **方法选择 + 原因**:
  - 搬 EDY 第 461 行:`τ_g = 2.128 · sin(θ − 1.438)`,大约占 MG4010 最大力矩的 47%。
  - 增益和相位要在实车上重新拟合:在几个角度上保持住,记录各自的稳态力矩,再拟合正弦曲线。
- **具体实现**:加一行前馈,两个参数。
- **验证**:不同角度下的稳态误差都接近 0。

## B3 — pitch 刚度项("粘滞前馈")

- **需求(问题)**:受扰动后 pitch 恢复偏软。
- **方法选择 + 原因**:
  - 搬 EDY 第 458–460 行。注意:这一项是在角度环的输出 `velocity_ref` 上计算的,所以实际效果是额外的角度刚度(约 10.6 N·m/rad),并不是真正的速度前馈。调参时要按刚度来理解。
  - 名字保留 RMCS 的叫法,但要在注释里写明它的实际作用。
- **验证**:轻拍枪管,恢复更快,且不振荡。

## B4 — 小 Yaw 居中

- **需求(问题)**:小 Yaw 是冗余轴,如果不控制,它会自由晃动。
- **方法选择 + 原因**:搬 EDY 第 424、429、434、451–454、467–469 行,目标恒为 0,角度 kp 45 → 速度 kp 2.16,粘滞项 0.231(同样相当于刚度)。
- **验证**:拨动小 Yaw 后,它会回到中位。

## B5 — 大 Yaw 编码器系闭环

- **需求(问题)**:大 Yaw 最终要在世界系里闭环,但应该先在最简单的编码器系里把回路和 reversed 符号验证清楚。RMCS 没有这一步,这里专门加一个台阶。
- **方法选择 + 原因**:角度 kp 12 → 速度 kp 22.5,反馈直接用编码器。
- **验证**:给编码器系下的目标角,大 Yaw 能平稳跟随,方向正确。

## B6 — 大 Yaw 世界系稳定

- **需求(问题)**:底盘小陀螺时,云台在世界系里必须保持不动。
- **方法选择 + 原因**:
  - 搬 EDY 第 372–382 和 423 行:
    - 大 Yaw 的世界角度 = 云台 IMU 的姿态,经 pitch 和小 Yaw 关节反算得到大 Yaw 的 x 轴,再投影到水平面,也就是 `bottom_dir = q_imu · Ry(−pitch) · Rz(−top) · eₓ`;
    - 大 Yaw 的速度 = 编码器速度 + 底盘陀螺。
  - 可以用 fast_tf 和 `sentry_description` 计算,也可以直接写几行 Eigen(结果等价,后者更直观)。
  - 需要 01 阶段 13 的云台 IMU 和阶段 10 的底盘 IMU。
- **具体实现**:大 Yaw 改为读世界系反馈,编码器系那条路径保留为调试参数。
- **验证**:底盘开小陀螺,云台朝向保持不变,摆动在几度以内。

## B7 — 失能捕获 + 无扰切换

- **需求(问题)**:解除急停的瞬间,如果目标还停在急停之前的位置,云台会猛甩过去。
- **方法选择 + 原因**:搬 EDY 第 317–342 行。`safety/enabled` 为假时,PID 复位、输出 NaN,并把当前的世界 yaw 和 pitch 捕获为新目标。
- **验证**:急停期间用手转动云台,解除急停后云台停在当前位置,不会甩回原位。

## B8 — 手动输入 + pitch 限位

- **需求(问题)**:要用摇杆和鼠标瞄准,并且不能超出机械限位。
- **方法选择 + 原因**:
  - 搬 EDY 第 88–102 行的增量式目标:`yaw += 0.006·joy + 0.5·mouse`,并做角度回绕。
  - pitch 限位 upper −0.39518、lower 0.36。因为正值代表向下,所以 upper < lower,`std::clamp` 的参数顺序也是对的。
- **验证**:摇杆和鼠标都能平滑控制;pitch 到达限位后停住。

## B9 — 给底盘的输出

- **需求(问题)**:A16 的"跟随云台"和"按云台系平移"需要知道大 Yaw 相对底盘的角度和控制误差。
- **方法选择 + 原因**:导出状态接口 `gimbal/yaw_angle`(大 Yaw 编码器角)和 `gimbal/yaw_control_error`,对应 EDY 第 46–48、344–369 行。RMCS 输出的 `/gimbal/yaw/velocity` 在哨兵上没有使用者,不搬。
- **验证**:A16 能够跑通。

## B10 — 导航指向(依赖 04)

- **需求(问题)**:决策层要能让云台朝某个方向看,比如扫描、看向目标点。
- **方法选择 + 原因**:
  - 搬 EDY 第 55–67、206–212 行:优先级是导航 > 自瞄 > 手动,切换时把当前目标拷贝给手动目标,保证无扰。
  - **修复坐标系不一致**:RMCS 的导航把目标换算到顶板 IMU 系(`OdomImu`),云台却在云台 IMU 系(`OdomGimbalImu`)里比较,两块 IMU 各自有零点和漂移。这里统一约定:进环的云台目标一律使用云台 IMU 系的 yaw。世界系到 IMU 系的偏置由环外估计(04 阶段 12)。
- **具体实现**:参考量入口 `gimbal_toward`(yaw, pitch),超时 500 ms。
- **验证**:发一个朝向,云台转过去;停发后云台回到手动控制,过程无扰。

## B11 — 自瞄方向输入

- **需求(问题)**:自瞄给出的瞄准方向要能驱动云台。
- **方法选择 + 原因**:
  - 搬 EDY 第 69–86、194–203 行:右拨杆 UP 或鼠标右键按下,并且方向是有效值时进入自瞄;`yaw = atan2(y, x)`,`pitch = atan2(−z, xy)`。
  - 数据来源是 D1 导出的 `aim/*` 状态接口。
  - 已知 RMCS 把世界系的 pitch 目标和编码器 pitch 做比较,车体倾斜时会有偏差。这一点先保持现状,列入触发清单:上坡时出现偏差,再改用 IMU pitch。
- **验证**:见 D2。

## B12 — 前馈与双 Yaw 耦合(依赖 D10)

- **需求(问题)**:跟踪运动目标时,纯反馈的云台会滞后。
- **方法选择 + 原因**:
  - 搬 EDY 第 433–461 行的 `velocity_ff` / `acceleration_ff` 通道,以及小 Yaw 对大 Yaw 的反作用耦合:`−k_top_to_bottom · (加速度前馈 + 粘滞 · 速度前馈)`。
  - 在 RMCS 里,这些前馈的数据源(自瞄 MPC 的角速率和角加速度)虽然注册了却没有接上,所以这条耦合项一直是 0。D10 接上数据源后,这一项才开始起作用。
  - 大 Yaw 摩擦前馈的符号值得怀疑(第 438 行用的是"世界速度 + 底盘陀螺"),启用时要实测确认。
- **验证**:见 D10。

# C. 发射

内容来源:`shooting/friction_wheel_controller.cpp`、`heat_controller.cpp`、`bullet_feeder_controller_17mm.cpp`;参数在 `sentry.yaml` 第 111–162 行。硬件见 01 阶段 12。

## C1 — 摩擦轮速度环 + 软启动

- **需求(问题)**:摩擦轮的目标转速是 630 rad/s,直接阶跃会产生电流冲击。
- **方法选择 + 原因**:
  - 结构和 RMCS 一样:`FrictionWheelController` 输出两个轮的目标速度,写入两个链式 PidController 的参考接口(kp 0.003437,kd 0.009373)。
  - 软启动搬第 120–140 行:复位后先用实测转速作为起点,每拍增减 `0.001 / T`(T = 1 s)。
  - 开关:V 键上升沿,或左拨杆 MIDDLE→UP 时切换(第 79–83 行)。
- **具体实现**:控制器 + 两个 PID,用一个 spawner 以 `--activate-as-group` 激活。
- **验证**:开启后约 1 s 平滑升到 630 rad/s;关闭时平滑降速。

## C2 — 摩擦轮健康 + 发弹检测

- **需求(问题)**:拨弹需要知道两件事:摩擦轮是否就绪,以及刚才是否打出了一发。
- **方法选择 + 原因**:
  - 搬第 177–236 行:
    - **ready**:已开启并且软启动达到 100%;
    - **故障**:转速低于目标的一半并持续 200 拍,判为卡住;
    - **发弹检测**:对转速下降量积分,积分小于 −14 并且转速已回升时,判为打出一发。
  - 修 RMCS 的问题:`friction_faulty_count_` 从不清零(第 186–191、264 行)。
  - RMCS 在右拨杆 DOWN 时输出不更新,会残留旧值;这里改成显式输出 NaN。
  - 这几个结果导出为状态接口:`shooter/friction_ready`、`friction_jammed`、`bullet_fired`。
- **验证**:手动喂一发弹丸,`bullet_fired` 跳一次。

## C3 — 拨弹单发

- **需求(问题)**:点一下打一发。
- **方法选择 + 原因**:
  - 搬拨弹控制器的单发部分(第 104–128、150–173 行):
    - 鼠标左键上升沿打开一个单发窗口,最长 2 s;
    - 窗口在 `bullet_fired` 时关闭;
    - 拨弹转速由射频换算:每圈 9 发。
  - 拨弹速度环用 PidController,kp 0.283。
  - 只有 `friction_ready` 为真时才允许拨弹。
- **验证**:每点一次,只打出一发。

## C4 — 热量

- **需求(问题)**:超过热量上限会扣血。
- **方法选择 + 原因**:
  - 搬 `heat_controller`:开环热量模型,每拍减去冷却值,每发加 `heat_per_shot`;`allowance = max(0, (上限 − 热量 − 预留) / 每发热量)`。数值以 ×1000 为单位(每发 10 热量,预留 1 发)。
  - 冷却值和上限来自 01 阶段 15 的裁判接口,超时回退值也已经在那里处理。
  - 裁判系统其实也给出了实测枪管热量,RMCS 已经解析(`field.hpp` 第 50 行)但没有用。开环模型漂移时再融合它,列入触发清单。
- **验证**:连续射击时,热量接近上限前会停止拨弹。

## C5 — 连发 + 安全射频

- **需求(问题)**:要能连续射击;热量只剩一发余量时要降速,避免超限。
- **方法选择 + 原因**:搬第 117–123、150–173 行。`allowance > 1` 时射频 28 Hz;`allowance == 1` 时 10 Hz;`allowance ≤ 0` 时停止。按住鼠标左键或左拨杆保持 DOWN 时连发。
- **验证**:连发时射频正确,热量逼近上限时自动降速。

## C6 — 卡弹检测与退弹

- **需求(问题)**:卡弹时拨弹堵转,不处理就会一直卡住。
- **方法选择 + 原因**:搬第 196–235 行。用一个 ±500 拍的积分器判断卡弹;前两次卡弹做反转退弹(15 Hz,0.15 s),之后改为深度退弹(0.20 s)。
- **验证**:人为制造卡弹,系统能自动退弹并恢复射击。

# D. 火控与自瞄控制侧(不含视觉)

**现状**(`rmcs_auto_aim_v2`):
- 视觉和火控都在一个独立进程 `runtime` 里;
- 这个进程和环内的 `AutoAimComponent` 之间通过 POSIX 共享内存通信:环内写入云台上下文,进程返回瞄准结果。

**切分线**:视觉输出 `Armor3d` 数组加上曝光时间戳(定义在 `utility/robot/armor.hpp` 第 61–68 行):
- 类型、颜色、编号;
- 位置:OdomGimbalImu 系,单位 m;
- 姿态:四元数。

切分线之后的模块(decider、EKF、弹道、选板、开火评估、MPC)都不依赖 ROS,只依赖 Eigen、yaml-cpp 和 TinyMPC,代码可以原样复用。

**策略**:先不改一行代码,把现有进程接进来(D1–D3);再在切分线把进程切开,把火控换成我们自己的节点(D4–D10)。

## D1 — 自瞄桥接控制器(沿用共享内存)

- **需求(问题)**:要让 RMCS 现有的自瞄进程不改代码就能接入新架构。
- **方法选择 + 原因**:
  - 把 `AutoAimComponent`(`component.cpp`)的内容搬进一个环内 `AutoAimBridge` 控制器。理由是共享内存的读写本身不阻塞(seqlock),RMCS 也是在 1 kHz 线程里做的。
  - 写入方向:每拍写一份 SystemContext,包括:
    - 云台 yaw 和 pitch,由云台 IMU 加关节角算出(第 50–69 行);
    - odom 到相机的变换,用 `sentry_description` 计算,相机相对 pitch 的偏移是 (0.07128, 0, 0.0481);
    - 机器人 ID,来自裁判接口。
  - 读取方向:读回 AutoAimState;超过 100 ms 的指令丢弃(第 115–119 行);结果导出为状态接口 `aim/{direction_x, direction_y, direction_z, should_shoot, valid}`。
  - 注意符号约定:上下文里 pitch 以向下为正,火控里以向上为正。这一点原样保留,但要在注释里写清楚。
- **具体实现**:
  - 复制 `kernel/feishu.hpp` 和 `utility/shared/{context, interprocess}.hpp`;
  - `runtime` 进程本身原样运行,只在 bringup 里加一个启动项。
- **验证**:启动 runtime 后,对着装甲板时 `aim/valid` 为真,方向读数合理。

## D2 — 云台接自瞄方向

- **需求(问题)**:要让云台跟着自瞄方向转。
- **方法选择 + 原因**:就是 B11,这里做联调。
- **验证**:右拨杆拨到 UP,云台锁定目标;目标丢失 100 ms 后退回手动控制。

## D3 — 拨弹接开火信号

- **需求(问题)**:自瞄模式下,由火控决定什么时候开火。
- **方法选择 + 原因**:搬拨弹控制器第 117–123 行:
  - 瞄准开关 `aiming_enable = 鼠标右键 || 右拨杆 UP`;
  - 进攻意图 `attack_intent = 鼠标左键 || 左拨杆 DOWN`;
  - 瞄准开启时需要 `should_shoot && attack_intent` 才开火,否则只看进攻意图。
- **验证**:自瞄模式下按住进攻键,只在对准目标时才拨弹。

> 到这里,哨兵已经具备 RMCS 的全部自瞄能力。D4 以后是把火控收回到我们自己维护的代码里。

## D4 — 记录切分线数据

- **需求(问题)**:火控逻辑锁在视觉进程里,无法离线复现和调参。
- **方法选择 + 原因**:
  - 只在 runtime 调用 `tracker.decide` 的地方(`runtime.cpp` 第 187 行)加一个输出:发布 `Armor3d` 数组加曝光时间戳。不改原有行为。这是对视觉进程唯一的改动。
  - 新建消息 `mvp_msgs/Armor3dArray`,这是领域消息。
- **具体实现**:十几行代码,加上一个消息定义。
- **验证**:对着目标录包,回放时能在 rviz 里看到装甲板的 marker。

## D5 — 火控节点:跟踪(在录包上)

- **需求(问题)**:要从装甲板观测估计目标机器人的整体状态(中心、速度、转速、半径)。
- **方法选择 + 原因**:
  - 新建 `mvp_fire_control` 包,原样复制以下纯 C++ 部分:
    - `module/tracker/decider`:目标选择,1 s 后丢弃目标;
    - `module/predictor/{regular, outpost}`:11 维状态的 EKF(4 块装甲板模型)和前哨站模型;
    - `utility/math/kalman_filter/ekf.hpp`。
  - 外面包一层环外节点,订阅 `Armor3dArray`。
  - 不选"放进环内":跟踪只需要跟着相机帧率跑,不需要 1 kHz,放在环外更便于调试。
- **验证**:回放录包时收敛标志能够成立;预测出的装甲板位置和观测一致。

## D6 — 弹道 + 飞行时间

- **需求(问题)**:弹丸会下坠,飞行期间目标也在移动。
- **方法选择 + 原因**:
  - 搬 `trajectory_solution`:二次空气阻力 k = 0.003,5 ms 欧拉积分,迭代求 pitch。
  - 搬 `target_solution_solver`:对飞行时间做不动点迭代,命中时刻 = 图像时间 + 飞行时间 + 发射延迟 0.07 s。
  - 弹速先用固定的 21.4 m/s。裁判给出的实测弹速 RMCS 没有使用,列入触发清单。
- **验证**:回放时,解出的 yaw 和 pitch 与 RMCS runtime 的输出一致(对比测试)。

## D7 — 选板

- **需求(问题)**:目标在旋转时,应该打哪一块装甲板。
- **方法选择 + 原因**:搬 `aim_point_chooser`:迎面窗口 70°、离去窗口 20°,优先选正在转过来的那一块;切换需要至少 8° 的改善(带滞回)。
- **验证**:回放时切板行为和 RMCS 一致。

## D8 — 开火决策

- **需求(问题)**:要判断什么时候可以开火。
- **方法选择 + 原因**:搬 `shoot_evaluator`:指令稳定(变化小于 2 倍容差),并且当前 yaw 与指令的差小于容差(近处 3°、远处 2°,以 2 m 为界),才允许开火。RMCS 只检查 yaw 不检查 pitch,先保持一致,列入触发清单。
- **验证**:回放时 `should_shoot` 和 RMCS 一致。

## D9 — 切换:火控节点进环,替代共享内存的读取

- **需求(问题)**:现在有两条火控路径(RMCS runtime 和我们自己的节点),需要切换到自己的节点。
- **方法选择 + 原因**:
  - 火控节点输出带 stamp 的"方向 + `should_shoot`",经 01 阶段 17 的参考量入口进环(超时 100 ms),写入 `aim/*` 接口。下游的 B11 和 D3 完全不用改。
  - 视觉进程仍然需要"图像时刻的云台上下文"来算 `Armor3d`,所以 D1 的写入方向(上下文写进共享内存)继续保留;只有读取方向被替换。
  - runtime 里的火控部分保留为对照,用参数控制是否启用。
- **验证**:实车自瞄效果不低于 D3;切回 RMCS 路径也只需要改一个参数。

## D10 — MPC 前馈进云台

- **需求(问题)**:打小陀螺目标时,纯反馈的云台会滞后。
- **方法选择 + 原因**:
